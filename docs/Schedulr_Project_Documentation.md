# 1. Executive Summary

Schedulr is a multi-tenant SaaS scheduling engine that generates mathematically guaranteed conflict-free academic timetables. An institution describes its reality once — who can teach what, which rooms exist and what equipment they have, how cohorts split into batches and electives, what rules must never be broken — and the system returns a timetable that is:

- **Provably correct** — verified by an independent conflict-checker (separate code path from the solver)
- **Optimally balanced** — soft preferences like faculty load balancing and room utilization are optimized via weighted objectives
- **Human-approved** — every generated timetable must pass through a mandatory Review → Approve → Publish workflow before becoming visible

The actual differentiator is not "it draws a grid." It is that the grid is provably clash-free at a scale no human scheduler can hold in their head, and it's re-proved cheaply every time something changes.

# 2. Problem Analysis

### The Real-World Scheduling Challenge

Academic timetable scheduling is an NP-hard combinatorial optimization problem. A medium-sized college with 40 cohorts, 100+ faculty, 50+ rooms, and 200+ course-cohort assignments faces a search space of billions of possible slot allocations. Manual scheduling — the method most institutions still use — suffers from:

| Challenge | Impact |
|---|---|
| Faculty double-booking | A professor accidentally scheduled for two classes at the same time |
| Room conflicts | Two cohorts assigned to the same room simultaneously |
| Workload violations | Faculty exceeding their weekly/daily teaching caps |
| Elective clashes | A student's chosen electives overlapping with their core courses |
| Lab scheduling | Multi-period lab blocks split across non-consecutive slots or different rooms |
| Iterative conflicts | Fixing one clash creates new cascading clashes elsewhere |
| Scale | Impossible to mentally verify all constraints across 200+ assignments |

### Why Existing Tools Fall Short

Most scheduling tools use either:
- **Greedy heuristics** — fast but produce sub-optimal results with frequent constraint violations
- **Manual drag-and-drop** — human-driven, doesn't scale, and provides no formal correctness guarantee
- **Rule-of-thumb algorithms** — cannot express the full complexity of real institutional constraints

Schedulr uses **constraint programming** — the same mathematical formalism used in airline crew scheduling and industrial logistics — to model and solve the problem with formal guarantees.

# 3. Solution Overview

Schedulr is built around three core principles:

### Principle 1: Mathematical Correctness Over Heuristic Approximation
Every generated timetable satisfies all 15 hard constraints by construction (enforced within the solver) and is independently re-verified by a separate conflict-checker module that uses a completely different code path.

### Principle 2: Human Control Over Automation
- Natural language rules are parsed but **never auto-applied** — they require explicit confirmation
- Generated timetables are **never auto-published** — they require reviewer approval
- The confirmation text shown to users is **template-rendered from structured data**, never re-generated by the LLM

### Principle 3: Tenant Isolation by Design
Data security is enforced at the database layer via Postgres Row-Level Security (RLS), not just at the application layer where a forgotten `WHERE` clause could leak data.

## 4.2 Key Architectural Decisions

| Decision | Rationale |
|---|---|
| **Solver as independent module** | Can be tested, scaled, and deployed independently of the API and UI (NFR-19) |
| **CQRS-lite pattern** | Generation writes raw `assignment` rows; Publish denormalizes into per-view read tables for fast queries |

| **Independent conflict checker** | A completely separate code path re-validates H1–H15 after every solve — we don't just trust the solver |
| **Database-layer tenant isolation** | RLS policies on every table, not just app-layer `WHERE tenant_id = ...` filters |

# 7. The Constraint Engine

This is the core innovation and the actual product. Everything else in the system is scaffolding around these constraint lists.

## 7.1 Hard Constraints (Zero Violations — Always Guaranteed)

Each constraint is enforced both inside the solver AND independently re-verified afterward:

| ID | Constraint | CP-SAT Formulation | Implementation |
|---|---|---|---|
| **H1** | No faculty double-booked in same slot | ∀ f,s: Σ assign[f,c,k,r,s] ≤ 1 | `build_h1_no_faculty_double_booking()` |
| **H2** | No cohort double-booked in same slot | ∀ k,s: Σ assign[f,c,k,r,s] ≤ 1 | `build_h2_no_cohort_double_booking()` |
| **H3** | No room double-booked in same slot | ∀ r,s: Σ assign[f,c,k,r,s] ≤ 1 | `build_h3_no_room_double_booking()` |
| **H4** | Faculty not scheduled during unavailable blocks | assign[f,*,*,*,s] = 0 for blocked s | `build_h4_unavailable_blocks()` |
| **H5** | Faculty only assigned to eligible (course, cohort) pairs | Variables only created for eligible combos | Enforced by construction |
| **H6** | Weekly hours per (course, cohort) exactly met | Σ assign = required_hours[c,k] | `build_h6_hours_match()` |
| **H7** | Slots within valid period range for day/shift | Variables only created for valid ranges | Enforced by construction |
| **H8** | Faculty weekly/daily workload cap never exceeded | Σ assign ≤ cap[f] per week and per day | `build_h8_workload_cap()` |
| **H9** | Room type/equipment matches course requirement | Variables only created for matching pairs | Enforced by construction |
| **H10** | Shared lab resource capacity not exceeded | Lab rooms at slot s: Σ assign ≤ room_count | `build_h10_shared_lab()` |
| **H11** | No student double-booking across elective combination | Cross-referenced via enrollment records | `build_h11_student_overlap()` |
| **H12** | *(Exam)* No student has overlapping exam sessions | Same as H11, applied to exams | `build_h12_exam_overlap()` |
| **H13** | *(Exam)* Room seating capacity not exceeded | enrollment_count ≤ room.capacity | `build_h13_exam_capacity()` |
| **H14** | *(Exam)* Invigilator not double-booked; within cap | Same as H1/H8, applied to invigilators | `build_h14_invigilator()` |
| **H15** | Block courses: N consecutive periods, same room/day | Occupancy s..s+n−1 in all sums; no day-boundary crossing | `build_h15_block_size()` |

## 7.2 Soft Constraints (Weighted Objective — Optimized)

These are penalty terms added to the solver's objective function. The solver minimizes total penalty while staying within the hard-constraint-feasible space:

| ID | Constraint | Optimization Target |
|---|---|---|
| **S1** | Minimize idle gaps for faculty and students | Gap penalty per person per day |
| **S2** | Balance faculty load evenly across the week | Variance in daily teaching load |
| **S3** | Distribute course hours across different days | Penalty for same-day stacking |
| **S4** | Prefer core/high-focus subjects earlier in the day | Slot-position weighting |
| **S5** | Minimize same-course-twice-in-one-day | Double-scheduling penalty |
| **S6** | Prefer parallel batch sessions aligned to same slot | Alignment bonus |
| **S7** | Maximize room-utilization efficiency | Unused-capacity penalty |
| **S8** | Respect faculty time-of-day preferences | Preference mismatch penalty |
| **S9** | *(Exam)* Spread student exams evenly; minimize consecutive-day exams | Gap-day bonus |

## 7.3 Constraint Rule Type Enumeration (Closed Set)

The NL parser and structured form can ONLY produce values from this closed enum. Anything unmappable routes to `unsupported` → manual structured form:

| rule_type | unit | Maps to | Example phrasing |
|---|---|---|---|
| `max_periods_per_day` | periods | H8 | "No faculty teaches more than 4 periods a day" |
| `max_periods_per_week` | periods | H8 | "Faculty should teach at most 20 periods a week" |
| `min_gap_between_periods` | periods | S1 | "Give faculty at least one free period between teaching blocks" |
| `no_consecutive_same_course` | boolean | S5 | "Don't put the same subject back-to-back" |
| `preferred_time_of_day` | morning/afternoon | S4, S8 | "Science should be scheduled in the morning" |
| `balance_load_across_week` | boolean | S2 | "Spread faculty load evenly across the week" |
| `room_utilization_priority` | weight | S7 | "Prioritize using all rooms evenly" |
| `elective_no_overlap_core` | boolean | H11 | "Electives should never clash with core classes" |
| `exam_min_gap_days` | days | S9 | "Give students at least one day between exams" |
| `unsupported` | — | none | Fallback → manual structured form |

## 8.2 Critical Design Principle

**The confirmation text is template-rendered from the structured JSON object — it is NEVER re-generated by the LLM.** This guarantees that what the user sees and confirms is exactly what gets stored and fed to the solver. There is no hallucination risk in the confirmation step.

## 8.3 Unsupported Rule Handling

If the LLM cannot map the user's input to a known `rule_type` from the closed enum, the system:
1. Returns `rule_type: "unsupported"`
2. Shows the user a manual structured form instead
3. Never silently drops or invents a new constraint type

# 9. The Solver Pipeline

## 9.1 The CP-SAT Decision Variable

The core of the solver is a single binary decision variable:

```
assign[f, c, k, r, s] ∈ {0, 1}
```

| Symbol | Meaning |
|---|---|
| f | Staff profile (faculty member) |
| c | Course |
| k | Cohort |
| r | Room |
| s | Time slot (block starting position, encoded as weekday × periods_per_day + period_index) |

**Meaning:** "Faculty f teaches course c to cohort k in room r, starting at slot s."

## 9.2 Variable Pruning (Correctness by Construction)

Variables are **only created** for combinations that pass these filters:
- `(f, c, k)` must exist in the `eligibility` table → **enforces H5 by construction**
- `(c, r)` must have matching room type → **enforces H9 by construction**
- `s` must be within the valid period range for that day/shift → **enforces H7 by construction**

This means infeasible assignments don't exist as variables — the solver never even considers them.

## 9.3 Solve Process

```
1. build_solver_input()
   ├── Load all faculty, courses, cohorts, rooms from DB
   ├── Load eligibility mappings
   ├── Load period templates
   ├── Load constraint_rules
   └── Load staff_availability_blocks

2. Create CP-SAT Model
   ├── Create BoolVar for each valid (f,c,k,r,s) tuple
   ├── build_h1() through build_h15() — add hard constraints
   ├── build_soft_objective() — add S1–S9 as weighted penalties
   └── If previous solution exists: AddHint() for warm start

3. Solver.Solve(timeout=SOLVER_TIMEOUT_SECONDS)
   ├── If OPTIMAL or FEASIBLE: extract assignments
   ├── If INFEASIBLE: return error with diagnostic info
   └── If timeout: return best-effort with soft shortfalls surfaced

4. conflict_checker.verify(assignments)
   ├── Re-validate H1–H15 using SEPARATE code
   ├── Return violations list (should be empty)
   └── If violations found: flag as system error, don't save

5. Save assignments to DB as DRAFT timetable_version
```

## 9.4 Incremental Regeneration

When a small change occurs (e.g., a faculty member becomes unavailable), the system uses CP-SAT's `AddHint()` to seed the re-solve with the previous solution's variable values. This means:
- The solver starts from a known-good point, not from scratch
- Small changes typically resolve in seconds, not minutes
- Hard constraints are still fully guaranteed in the new solution

# 10. Independent Conflict Verification

This is a non-negotiable architectural invariant: **solver output is never trusted on its own.**

## 10.1 Why a Separate Checker?

A bug in the solver's constraint construction would produce incorrect output that the solver itself would believe is correct. The independent conflict checker uses a completely different code path to validate the same rules:

| What the Solver Does | What the Checker Does |
|---|---|
| Adds `AddAtMostOne` constraints to the CP-SAT model | Iterates over all assignments, builds per-slot dictionaries, checks for duplicates |
| Uses variable construction to enforce eligibility | Joins assignments against the eligibility table and flags mismatches |
| Encodes workload caps as linear constraints | Counts assignments per faculty per day/week and compares to caps |

## 10.2 Checker Output

The conflict checker returns a structured report:
```json
{
  "hard_violations": [],       // Must be empty for a valid timetable
  "soft_shortfalls": [         // Informational warnings
    {"type": "S1", "entity": "faculty_123", "detail": "2-period gap on Monday"}
  ],
  "verified_at": "2024-01-15T10:30:00Z"
}
```

If `hard_violations` is non-empty, the timetable version is flagged and cannot proceed to review.

# 13. Multi-Tenant Architecture & Security

## 13.1 Identity Model

One person (Identity) can hold staff/student profiles at multiple institutions:

```
Identity (alice@example.com)
    ├── Staff Profile at Tenant A (Professor, Admin role)
    └── Staff Profile at Tenant B (Adjunct, Faculty role)
```

## 13.2 JWT Design

The JWT carries **only** `identity_id` (as `sub` claim) — **never** `tenant_id`. Tenant context is resolved per-request from the `{tenantId}` URL path parameter.

## 13.3 Database-Layer Isolation (RLS)

Every tenant-scoped request sets session variables before any query:

```sql
SET LOCAL app.tenant_id = '<tenantId>';
SET LOCAL app.identity_id = '<identity_id>';
```

Every table has an identical RLS policy:

```sql
CREATE POLICY tenant_isolation ON <table>
  USING (tenant_id = current_setting('app.tenant_id')::uuid);
```

This means even if application code forgets a `WHERE tenant_id = ...`, the database itself will filter out other tenants' data.

# 18. What Makes Schedulr Different

| Aspect | Typical Scheduling Tool | Schedulr |
|---|---|---|
| **Correctness guarantee** | Best-effort heuristic | Mathematical proof via CP-SAT + independent re-verification |
| **Rule input** | Checkboxes and dropdowns | Natural language with deterministic confirmation |
| **Trust model** | Trust the algorithm | Don't trust — independently re-prove every output |
| **Publish control** | Auto-save | Mandatory Draft → Review → Approve → Publish |
| **Confirmation integrity** | LLM generates confirmation text | Template-rendered from structured data (no hallucination risk) |
| **Tenant isolation** | Application-layer WHERE clauses | Database-layer RLS policies |
| **Incremental updates** | Full re-generate from scratch | Warm-started via AddHint() |
| **Elective handling** | Cohort-level only | Individualized per-student schedule |
| **Extensibility** | Monolithic | Solver is independently deployable; exam module slots in without changing solver core |
